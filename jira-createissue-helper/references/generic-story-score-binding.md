# Generic Story score binding

Use only after selecting a non-SDLC generic create, update or batch route for a Story. Do not load this for other issue types, Test Cases, associations or SDLC handoffs. This is a conditional post-export database association, not scoring or a Jira field update: every eligible scored Story must be bound; unscored Stories are skipped.

Before the existing generic preview, identify per Story whether the current conversation or a supplied/known result file proves a completed Workspace call to `score_requirement_markdown` for the content being exported: `ok === true`, finite numeric `finalScore`, and the exact Workspace-relative `.md` input used as `relativePath`. Read the result and input when needed; the input must still represent the exported Story apart from Jira transport formatting. For a batch, record each item's index, effective issue type, score eligibility and input path in the existing preview. The score-result file is never the binding path. A low score, including 0, is eligible; do not apply the SDLC score gate. If evidence is absent, stale or ambiguous, export normally without binding and report that the score was not associated. Do not call the scorer during export. A Jira-mode score is already associated by the scoring tool and does not use this path-based binding.

For each eligible Story, include the intended score binding and input path in the existing `jira-preview.md` and generic confirmation. Keep the first Jira export payload unchanged and omit `markdownReviewRelativePath` from it. The existing confirmation covers the displayed export and conditional binding plan; do not add a second popup.

After a confirmed successful Jira create/update, use only that item's confirmed returned Ticket Key. For a batch, keep the one batch issue-write call, then match each returned resource to its previewed item index and handle every successful eligible Story separately. A missing/ambiguous resource or Ticket Key remains pending, never guessed. Call `exportJiraByDynamicFields` with exactly five nonempty direct arguments: `staffId`, `almType`, `issueIdOrKey` (that Ticket Key), `conversationId` (the scoring Workspace's real conversation identity), and `markdownReviewRelativePath` (the same input path passed to the scorer). Do not pass the score-result path or Jira content/attachment fields. If the scoring Workspace or conversation ID cannot be verified, do not guess or bind; report the missing prerequisite for that item.

Treat the association as successful only if the returned `markdownReview` confirms it. Before closing a batch, account for every item as bound, unscored/already Jira-associated, write-failed, or binding-pending with its reason; do not mark an eligible item complete merely because the batch issue-write call succeeded. Report Jira write and database binding separately. A failed, partial or uncertain binding leaves the successful Ticket intact: do not repeat its create/update/attachments or automatically retry the binding.
