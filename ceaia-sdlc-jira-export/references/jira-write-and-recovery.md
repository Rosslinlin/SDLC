# Preview, path-only submission and backend recovery

Use a [current validated handoff](handoff-and-content.md), verified assembly and authorized [attachments](attachments.md). Tool: java-base-mcp.exportJiraByDynamicFieldsV2. The user-confirmed interface has exactly one argument, story_json_workspace_path. There is no separate five-field B call. See [examples](call-examples.md).

## 1. Preview the actual scored package and obtain confirmation

1. Inspect the exact saved .json4jira and every scored/intended-upload SPEC, reusing complete unchanged tool-returned contents with actual path/revision evidence where available. Verify both root Wiki paths and their current file-revision bindings against the passing score without agent-side Wiki dereference. Verify SPEC review/score/header/currentness and selected global coverage under the handoff without repeating content-quality review. A new stage/Skill alone is not a reason to re-fetch the same full data. Do not serialize a replacement request or query metadata here; final pre-submission read-back is still required.
2. Present that actual .json4jira using the platform's native frontend preview. Its Code view keeps root descPath/acPath references; its Preview resolves and displays the full Description and AC from the two distinct Wiki files. Show create/update operation, source/project/Story type, the update's exact root issueIdOrKey, full business content, synchronized local SPECs and the saved required root `attachmentsJson.add` entries. Show the new files and that all existing attachments are retained. Verify the [approved upload plan](attachments.md). Story-only wording does not exclude SPEC synchronization. Create files omit issueIdOrKey. The platform may render HTML; this is not an instruction to generate another HTML upload file or invent a preview tool. If native preview cannot resolve both Wiki bodies or current-content confirmation is unavailable, retain the prepared files and return the precise WAITING_TOOL.
3. Obtain an explicit user content/upload confirmation for this current package through the supported platform confirmation capability. Initial SDLC intent, earlier destination settings, a previous revision's confirmation or a model-written label does not count. Reuse an existing actual confirmation only when it binds these same current JSON, both Wiki files and SPEC files with their revisions. The user may confirm several clearly identified current packages together.
   Use a friendly, concrete invitation, for example: “These are the Story and SPEC files prepared for export. Please review the files, including the content, project and attachment operations. Confirm export when everything looks right, or tell me what you would like to change.” Link the actual files and state the selected effects; do not present internal schema/checksum instructions as user decisions. This remains explicit confirmation, never an automatic export after silence.
4. Resolve `exportPreparation.previewPath` to `<paths.historyRoot>/jira-preview.md` before saving. Keep this compact internal record: exact one-argument invocation, JSON path/revision, both Wiki paths/file revisions, SPEC paths/file revisions, target/attachment summary and actual native-preview/confirmation evidence. Use the full resolved Workspace-relative path and verify the returned save path is inside historyRoot. Record exportPreparation.previewConfirmation as status=confirmed with storyJsonPath, storyJsonRevision, descWikiPath/descWikiRevision, acWikiPath/acWikiRevision, specFileRevisions entries {path,fileRevision}, and this actual recordPath. Native preview already exposes the resolved Wiki business content; do not copy/re-author JSON, Wiki or SPEC bodies into another preview artifact. Never use a bare jira-preview.md or outputRoot fallback. If internal storage is unavailable, preserve the prepared package and return that precise WAITING_TOOL.

An edit in the frontend changes the submission input. Return it to generation to recheck the Story package, align affected tests/SPEC/projection, obtain SPEC-only independent review where affected, synchronize headers where affected and obtain a new score and current-content confirmation. Any JSON or referenced Wiki edit, including destination/attachment/schema-only JSON edits, invalidates score and confirmation; an affected SPEC edit also requires fresh SPEC review. Never modify, rename, normalize or reserialize JSON, Wiki or SPEC between passing score and submission.

## 2. Record the actual invocation and submit the unchanged path

Resolve `paths.historyRoot` before any attempt save. When the export invocation is actually issued, allocate its next unused `<historyRoot>/jira-export-attempt-<nnn>.md` and increment exportAttempt once. Bind current scoreRecordPath/scoreAttempt, actual score input, matching Assembly section in preparation.md (or actual legacy record), review/global-coverage records, exact preview/confirmation and final read-back observations. Preserve the exact one-argument request and complete actual response/error in this same attempt and verify the returned save path. Completed attempts are immutable. Previewing, inspecting an old result, waiting/resuming and retrying a local save do not create another numbered attempt; a tool call never made has no export-attempt record.

Immediately before submission read back the actual approved JSON and every scored/intended-upload SPEC, verify both Wiki paths and their current revisions through the available platform evidence, and check all bindings against the score and confirmation. Recheck the [required add plan](attachments.md) for a nonempty add array with the exact reviewed upload paths. Return any invalid plan upstream before calling the tool. Do not independently read or transform the Wiki bodies. An immediately preceding complete current read can satisfy this check; neither stale snapshots nor counters alone do. Do not repeat another identical fetch without an intervening write or currentness gap. An update's root issueIdOrKey must be nonempty and equal the confirmed saved target; never remove it to pass create validation or redirect to another issue. Copy story_json_workspace_path unchanged from the passing score input and paths.storyJsonPath. attachmentsJson remains a native object in that file; do not pass it, issueIdOrKey or other direct content/routing/identity/attachment fields, SPEC parameters, requestJson/issuesJson or internal handoff/state metadata as extra tool arguments. Platform identity/session headers are not caller-generated arguments.

Call the exporter once for this candidate. The backend must resolve the JSON's two Wiki references into the outgoing Jira Description and mapped AC fields, validate the stored score/current content/threshold, execute the supported issue/attachment operation, link the score record to the Jira ticket in the database and enqueue asynchronous Jira score synchronization. Agent-side PASS or a saved local report does not replace those backend effects. Do not issue B to perform them again.

Multiple candidates use one path per sequential call, in confirmed selection order. Each has its own score and current-content confirmation. Stop subsequent **Jira submissions** at the first failed/partial/unknown required synchronous outcome, preserving remaining candidates; this never stops the successful issue's independent profile closeout below. Confirmed queue acceptance with asynchronous sync pending is not itself a submission failure.

## 3. Read the complete response and record each effect

Preserve the full raw result before interpreting it, including unknown fields/errors and returned service IDs. For an already decoded object serialize the whole object and label that mode; do not claim byte-verbatim text. Inspect nested business failures even when an MCP envelope has isError=false; status=400 or a checksum/threshold rejection is not success.

Use the actual live response schema/guarantees. These are local observation categories, not invented backend field names:

| Outcome | Evidence required |
| --- | --- |
| issue | Actual supported create/update success and unambiguous returned ticket identity/URL when exposed. An update's returned key must match its reviewed target. Do not infer keys from positions or ambiguous numbers. |
| attachments | Record every required new SPEC upload from actual response evidence or an applicable documented guarantee. An existing attachment removal is outside the approved plan. |
| databaseLink | Explicit association evidence or a documented response guarantee proving score-record-to-ticket linkage. A ticket key alone does not prove it. |
| scoreSyncQueue | Actual accepted/enqueued result or a documented guarantee. Keep the real queue/score record ID when returned; do not manufacture one. |
| jiraScoreSync | Actual completed/failed/pending evidence. Queue PENDING/accepted proves scheduling, not a Jira UI score-field update. Without completion evidence report pending/unknown. |

An authoritative response may prove several effects when its documented semantics guarantee them; record that basis. A generic success with no such guarantee does not prove every effect. Missing optional IDs alone are not failure, but required effects without evidence remain unknown/pending.

Before any final/partial return: retain the issue result → if issue success is confirmed, execute [profile closeout](workspace-profile.md) using ordinary Workspace/file operations → record other effects internally and stop later Jira submissions where needed. Local audit-save or attachment/linkage/queue failure never skips eligible profile closeout. Unknown issue results need supported read-only reconciliation, never invented success or Jira replay.

Preserve the full raw response once in the internal attempt record; save compact observed states/evidence pointers in state.writeResults rather than copying the response into several reports.

The default completion message contains only the confirmed Jira result/key/link, available Story score and current deliverable links. Each link label equals the real filename, including extension and case: new files use story.json4jira, both actual .jirawiki filenames, test-case.md and the existing <name>-spec.md; do not use generic Story JSON/Test cases/SPEC labels. A verified profile save may be acknowledged briefly as settings saved for next time. Do not add routine SPEC upload, score synchronization, database linkage, queue, HTTP status, task/record IDs, Q1-Q7 checklists or loaded-Skill sections; retain those details in existing internal records and provide them only for requested diagnostics. If a failure or unresolved requirement affects delivery or completion, state the practical limitation and next action in one short plain-language sentence; never hide a real incomplete result behind an all-complete claim. Normal accepted asynchronous processing needs no extra user status line. Keep process-file links out of the default delivery list.

Synchronous submission is complete only with confirmed issue, required attachments, linkage and enqueue; it may finish with score synchronization pending. A current local SPEC does not prove the remote SPEC changed, and a pending required SPEC operation prevents claiming full Story/SPEC synchronization. Never state the Jira UI score is synchronized merely because the call returned or a queue row exists.

## 4. Partial, failed or unknown outcomes

- A failed local response save retries that save, not the external operation. Preserve a received response even if later interpretation fails.
- Known issue success with attachment, linkage or queue failure keeps the ticket and all confirmed uploads. Do not recreate/update it again or resend confirmed files to repair another effect. There is no automatic legacy B, generic-helper fallback or standalone upload/delete bypass.
- Unknown timeout/connection loss is unknown, not not-started. Use only actually available supported read-only reconciliation. A Jira read may establish ticket/attachment state, not database/queue state. Before returning WAITING_TOOL for unresolved effects, run the response closeout above whenever the issue itself is already confirmed successful; otherwise keep its outcome unknown. A vague continue does not establish idempotency.
- A validation/checksum/threshold rejection requires actual evidence of whether any effect occurred. Return stale/invalid inputs upstream for bounded correction, affected SPEC review where needed, scoring and fresh confirmation. Do not drop fields or alter a scored file at the submission step. Only documented failure proving no external effect permits a new attempt after the required correction/confirmation; no blind automatic retry.
- If a new upload failed or is unknown, retain the actual outcome and all existing and confirmed uploaded files. Use only focused supported recovery after reconciling uncertain outcomes. Preserve historical removal outcomes as evidence, without attempting to complete an old removal.
- Asynchronous queue processing is backend-owned. Do not invent polling/recovery tools, loop waiting for completion or re-export to nudge a job. Retain actual pending/failed sync internally; surface only a practical completion limitation/next action under the concise completion wording above.

Local records/counters are audit evidence, not remote locks or database proof. Preserve known/unknown outcomes on resume and use the single response closeout above; missing result/recovery capability never authorizes fabricated success. Profile-only recovery never replays Jira, uploads or scoring.
