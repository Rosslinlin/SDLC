# CEAIA JSON-first workflow — contract 7

Version 6.1.0-preview.10 — 2026-11-09. This contract owns orchestration, state, invalidation and bounded repair. Content criteria belong to [Q1–Q7](quality-contract.md); JSON field mapping belongs to [assembly](jira-json-assembly.md); actual scoring belongs to [scoreUserStory](scoring-tool-contract.md). Task and ordinary chat use this same sequence. Runtime is text-only on GPT-5.6 Luna or GPT-6 Luna.

## Fixed sequence

| Phase | Action | Output / next |
| --- | --- | --- |
| intake | Classify targets, confirm each Jira source, read original evidence and update baseline/inventory. | Fixed selected list; each target ready or precisely pending. |
| assemble | Read real persistent user-Workspace profiles and current baseline. Actual missing/no applicable saved profile uses source → project → optional extra fields, even if source/project are supplied; record the extra-field answer or explicit skip. Existing profiles require approval of the displayed settings before canonical files. SDLC stays Story. Reuse shared components across create/update and query only missing/inapplicable facts. Resolve required values and the automatic SPEC delivery plan. | Complete final story.json4jira and assembly snapshot, not a future export TODO. |
| generate | Derive or synchronize tests and every affected Markdown SPEC from the saved JSON and approved delta, without needing separate update-SPEC wording; perform one precheck. | Actual consistent JSON, tests and all SPECs. |
| review | Fresh read-only reviewer reads sources and current JSON/tests/SPECs. Parent saves its report. | PASS → score; supported defect → affected repair/review; missing fact → clarification. |
| score | Parent synchronizes every SPEC Result/Notes and verifies unchanged bodies, then calls scoreUserStory on the JSON with SPEC status/path and saves the complete response. | Current passing score; JSON and all scoring inputs frozen. No score write into SPEC and no display-only S2. |
| global-coverage | Reconcile all original obligations against every selected candidate, current evidence and approved exclusions. | Zero pending obligations before the integrated export stage. Preparation-only ends here. |
| preview | Present the actual scored JSON through the platform's .json4jira preview and obtain explicit content/upload confirmation. | Confirmation bound to the current JSON and SPEC revisions. |
| export | Call the path-only exporter on each confirmed file, unchanged. | Actual issue/attachment/database-link/queue results; asynchronous Jira score-sync status separate. |

Default jiraExportRequested=true without needing export wording. Entry is Jira-backed; never show a preparation-only/Jira-backed delivery-route selector or recommend dropping Jira because configuration is missing. Follow assembly's first-entry path: read actual persistent user-level profile/context, select the applicable project/Story settings and obtain the early settings decision under assembly, asking only missing business inputs, querying only the remaining applicable schema and offering optional extra fields after their actual support is known. Missing inputs retain Jira intent during a resumable wait. Only the user's explicit preparation-only/no-Jira, scope change or stop changes that intent; do not solicit that exception as a setup shortcut. Preparation-only skips submission, not the real configuration needed for final JSON/scoring. Stage-only invocations stop at the assigned boundary without cancelling later whole-workflow intent. Before first submission, missing optionalFieldsDecision evidence returns to assembly, never export-side intake or a new review/score just for control evidence. Once issue success is confirmed, profile-only recovery bypasses this preparation question and preserves unknown historical evidence; resolve the decision only for a new preparation. Prepare one ready candidate through assemble/generate/review/score at a time. Blocked candidates remain selected; they do not prevent unrelated preparation. All selected scope and global coverage must pass before integrated export unless the user explicitly changes scope.

## Files and resources

This includes `outputs/ceaia`, `.ceaia-work`, candidate/batch state, preparation, baselines/inventory, extracted source copies, previews and review/score/export records. These relative directory names do not select a storage scope. Resolve them against the actual session destination using supported tools/native actions; never reuse a user-Workspace destination binding for these writes. Use the existing save/read-back checks, not additional probes, reports or verification loops. If session storage is unavailable, report the precise affected operation; user Workspace is not a fallback.

The sole persistent user-Workspace write in this workflow is the reusable configuration file `ceaia-sdlc-jira/profiles.json`, under the profile procedure. Its persistence state, snapshot and operation evidence stay in session records; `profilePersistence.scope=user` describes the profile destination only. Read original user-provided sources where they actually exist without moving or rewriting them. Use actual platform destination selectors/context; do not invent a scope argument or add a session/user prefix to tool paths.

## Bounded repair and persistence

Default two content-repair batches per candidate/evidenceRevision, shared across review and score findings. Fix all known supported defects in one batch, increment round/cumulativeRounds once and independently verify affected content. Stop early when the same material blocker remains without progress. Do not change scope or cosmetically mutate content to seek a better score.

Pure mechanical corrections have at most one correction/check per real cause, tracked by causeId/artifactPath/attempts/outcome in technicalRecovery.mechanicalCorrections. They do not consume a content batch, but changed scoring inputs still invalidate score/confirmation. Backend JSON validation errors identify exact corrections; canonical inputs still failing are a technical issue. Missing business facts wait immediately under [clarification](user-clarification-and-resume.md). New substantive evidence resets only the affected active counter; finite extra rounds require actual recorded user direction. Resume never resets consumed state.

The local repair allowance never authorizes replaying an external create/update/upload. Preserve complete response records. A failed local save retries saving the received response, not the tool. Unknown scoring or creation outcomes require supported reconciliation rather than blind replay. The new route has no separate B call; never send old five-field arguments to recover backend linkage or queue failures.

A run-only override never becomes a stored default.

Pass handoff through existing state/record pointers, not another handoff Markdown file. Use the exporter completion wording: omit routine technical outcome/status sections, keep their evidence internal, and state any delivery/completion limitation in one plain-language sentence with a next action when needed. ## Migration from v6

The 2026-11-03 confirmed fields/AC-ID-map format also supersedes preview.1's flat JSON. Before an unsubmitted package continues, generation rewrites it using actual metadata, aligns its dependent SPEC/tests, verifies affected review and obtains a current score and content confirmation. A schema-only edit still changes scored bytes. Preserve old records and every known/unknown remote outcome; an already submitted or uncertain operation is reconciled, never recreated to migrate its format. State contract remains 7 because the control-state shape is unchanged.

The current file contract keeps the AC ID at root acceptanceCriteria, removes customFields, and confirms root issueIdOrKey for updates only. Reporter is now conditional on actual operation metadata and a resolved required or explicitly requested value; legacy reporter values are not copied automatically. Use the matching create/update template before scoring. For an update, bind that exact nonempty key to the actual baseline/source/target; never infer it from an evidence ticket or profile, and never remove it to retry as create. The selector is not an extra score/export tool argument. Separate unsupported attachment operations remain specific capability gaps, not a reason to label the confirmed basic update target unknown. Migration changes scoring inputs and needs a current score/confirmation; preserve all remote-outcome evidence.

Preserve old state, original inputs, score records and every known/unknown remote outcome as migration evidence before converting local metadata. A Markdown score or old five-field association cannot authorize a new JSON upload. An unexported candidate must assemble the actual JSON, regenerate dependent views, independently review and score it through the new interface. Remove old storyPath/storyRevision/specScoreDisplay only after their evidence is preserved; new control uses storyJsonPath/storyJsonRevision. For an earlier fields-based JSON, follow [format migration](jira-text-format.md): remove root staffId and encode authored Jira rich text before rescoring/reconfirmation. Recheck affected semantic consistency; presentation-only changes do not justify a whole business rewrite. Never migrate by replaying a known/unknown remote write.

For an already-created ticket with an old pending B or unknown attachment result, do not automatically rescore, recreate or send old B arguments to the path-only tool. Keep that operation pending until a genuinely supported backend recovery/association method is established. Migration never converts unknown into not-started. The former v6 bundle remains in Git history; main now follows this JSON-first contract, with no automatic legacy fallback bypassing the backend gate.
