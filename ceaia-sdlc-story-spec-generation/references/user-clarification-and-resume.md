# Content clarification and bounded resume

Read only when a review/final-score blocker needs user input, including exhausted repair allowance. Generation owns this interaction; the independent reviewer remains read-only. This does not replace Jira source/settings questions, technical recovery, or the shared one-round repair policy.

## Explain in chat, ask briefly in the popup

1. Read the latest actual findings and affected saved content. Before asking, show one compact chat entry per remaining material blocker, in the user's language:
   - Actual full workspace-relative file path and section plus AC/FR/TC ID, or another precise heading/table-row locator. Include a line only when actually known.
   - A short quotation of the current problematic text, or identify the exact missing item; do not invent a quotation for absent content.
   - The specific defect, its source evidence/conflict or missing fact, and why it prevents acceptance or an executable test. Never stop at "AC is wrong" or a score label.
   - The exact fact/decision needed and the affected files to update afterward. Use current report evidence; do not copy full source documents or raw score JSON into chat.
2. Distinguish missing/conflicting business information from an AI writing defect. For a genuine missing fact, ask only for that fact. If existing evidence already determines the correct behavior but the repair allowance is exhausted, explain the missed implementation and ask whether to apply **one additional repair batch** to the named candidate(s). Do not make the user restate known requirements. Tool/parser failures follow technical recovery instead of fabricated business questions.
3. Save the compact pending binding in `state.userRecovery` before calling `ask_user_question`. When available, this tool is required for the actual answer/decision; chat explanation alone is not the question. Use the live tool schema, without inventing popup parameters or limits.
4. Keep each popup question to about three short text lines: **unique shortened file/item locator; one-sentence reason; one concrete question**. Full paths and detailed evidence stay in the preceding chat entry. Include enough context to answer without a generic "see above". Use the candidate folder when a basename alone is ambiguous. Do not paste the report, multiple paragraphs, internal state/score paths or JSON into the popup. Use supported choices only when meaningful; allow a written business answer. An extra-repair choice must explicitly name its finite count/scope; defer/stop remains available.
5. Group related blockers that depend on the same business decision rather than opening one popup per finding. Prefer at most three short related questions per interaction, subject to the live tool's capabilities; this is a presentation target, not a claimed API limit. Keep unanswered material questions pending. After asking, set userRecovery.status=pending, state.status=WAITING_USER and nextAction=await-content-answer with readiness false, then yield; no edits, review, scoring or export for the blocked candidate while awaiting an answer. If the tool is unavailable, preserve the existing once-only text-question fallback.

Illustrative popup wording only, not a real finding or assumed business rule:

> `checkout/STORY.md · AC-003 (submission timeout)`
> The required timeout flow has no data-retention rule, so its expected result is undefined.
> After a submission timeout, should the entered data be retained?

## Bind and apply the answer

- `userRecovery` holds status (`none/pending/answered`), kind (`clarification/extra-repair/mixed`), evidenceRevision, reviewAttempt, detailRecordPath, answerRecordPath, questions and an actual tool questionRef if exposed (otherwise null). Each question has a stable local id, findingIds, artifactPath, itemLocator, exact missing fact or finite repair decision, question text and pending/answered status. Store only this compact binding, not document bodies; initialize missing recovery state on older workflows without resetting repair counters.
- Associate each answer with its candidate, question and actual current item. Re-read affected content if it may have changed. Record the supplied fact/decision and source in the next numbered planning revision. Preserve the original evidence and review reports; never overwrite history or silently treat unrelated text as an answer.
- A substantive business clarification/decision follows the shared evidenceRevision rules: invalidate only affected gates, reset the affected revision's active allowance to one, and retain cumulative repair/review/score counts. It is not an unlimited retry grant. If the answer only authorizes one extra repair, keep evidenceRevision unchanged, add exactly one scoped extra round before editing, and retain consumed counts. "Continue", dismissal, a new session or restating an existing fact does not by itself supply new evidence or authorize an extra batch.
- If an answer is incomplete or ambiguous, save the useful part and ask only the remaining specific fact in a concise follow-up; yield again. Do not repeat answered questions, infer missing business behavior, or regenerate files after every partial answer. Resume artifact changes when the affected candidate's material business questions are answered and its edit allowance is valid; remaining source-backed artifact defects belong in that permitted batch. A sufficient business answer resumes the requested workflow without a redundant "continue?" popup. Apply each bound answer/repair authorization once; on resume, use its answerRecordPath and current state rather than granting another extension or resetting evidence again.
- Once the answer is sufficient and an edit is permitted, set state.status=IN_PROGRESS and nextAction=regenerate-affected-artifacts. Reassess impact and update the affected planning/Story, then dependent Test Case and every affected SPEC/embedding. Keep correct unaffected content, candidate identities, filenames and update preservation mappings. A Test Case/SPEC-only change does not rewrite a correct Story; do not regenerate the whole batch for one answer. A defer/declined extension preserves the pending work and yields without repeating the popup; an explicit stop follows STOPPED, never PASS.
- Read back the changed files and run independent review of every invalidated gate plus cross-artifact consistency. The earlier PASS/score never approves changed content. After current PASS, synchronize SPEC headers, perform the existing Workspace score/parser/76 gate and score-display finalization, then continue through the existing validated Jira handoff. Reuse still-current results for unaffected candidates; no duplicate Jira/attachment/database writes. Mark recovery answered when its questions are resolved; a new blocker gets a new binding under the same bounded rules.
