# Assemble final Jira JSON during Story generation

This step moves the former export-time project/type/field discovery, value resolution and payload assembly **before final scoring**. The exporter will only transmit the saved path. Use existing tools, no scripts, speculative fields or new query APIs.

Only profile operations on `ceaia-sdlc-jira/profiles.json` use user Workspace. Save all generated JSON, its two referenced Jira wiki files, SPECs, tests, Assembly snapshots and other process records in the current **session Workspace** under the workflow contract; profile lookup must not switch their destination to user storage. Reuse a working operation only with the appropriate destination binding, and keep scoring/export paths unchanged and session-relative.

## 1. Reuse profile components, then query only missing facts

### First entry and settings confirmation

Keep the default Jira-backed workflow. Do not offer a delivery-route choice between preparation-only and Jira-backed or recommend no-Jira because setup is missing. SDLC always prepares **Story**; an Epic/Bug profile never changes the issue type of this route. Use this short path before authoring a new candidate's canonical JSON:

1. Read `ceaia-sdlc-jira/profiles.json` through actual platform-supported file/folder operations at the user destination, including ordinary tools or native file actions executable by the current agent. Reuse a successful operation only when that mechanism is actually available; a chat creation claim, code block or path is not proof. A documented destination selector or implicit authenticated namespace suffices; no dedicated user-level tool name, returned scope field or extra identity proof is required. Match authenticated user/source/project/actual Story type, keeping operation-scoped defaults/permissions separate. Read legacy `storyType` as Story and write consistent canonical `issueType`/Story alias; conflicting IDs are not guessed. Preserve other projects/types and reuse only applicable stable facts across create/update.
2. Actual not-found or no applicable saved entry triggers **source → project → optional extra fields**. Source/project already supplied skip those questions, not the third decision. An uncertain/failed read is not a found profile or an answered question; retain the error and preserve the existing store. Do not ask for staffId at routine intake or ask users for technical type/schema/AC IDs; a project name is sufficient. A required Reporter with no verified value follows the conditional question below. Multiple real destinations need selection, never a first/last-used default.
3. Query only missing applicable project/Story-type/field facts. A confirmed project key goes directly to supported type/metadata queries, not an invented project-key search argument. Only for first use with no applicable saved settings, once actual field choices are known, ask once. For a create: “For future Stories in [source/project], would you like to use any additional supported fields, such as Epic Link, Components or a custom Story Type? Values you give here will be used for this Story and remembered for later creates. Say ‘this Story only’ for any exception, or ‘Skip for now’.” For an update, ask only which supported fields to change on the actual target and whether any should be remembered as future update preferences; never frame target/baseline values as future create defaults or apply create defaults to the ticket. Use real supported labels/options; do not present examples as available fields. If the user already supplied a field value, include its actual name/value in this same question and resolve future use versus this run only; do not add another questionnaire. If Reporter is actually required for a submitted value and unresolved, combine its needed staff-ID question with this settings question when possible, including whether the resolved Reporter should be remembered or used only now. Custom Story Type never changes SDLC from Story. Unsupported requested mappings stay precise gaps; optional skips do not block and required facts remain separate. With no other selected Epic, “Skip for now” also means no Epic for this run, without erasing an existing choice or becoming a permanent default.
4. Before new authoring, resolve `exportContext.assembly.optionalFieldsDecision` in the existing Assembly record: `provided` means first-use extra fields or an explicit future-default change, with a per-field future-default or this-run-only decision; `skipped` means explicit no-extra-fields; `reused` means actual current-run approval of displayed saved fields/defaults, including a recorded one-off override of that approved configuration. A matching explicit answer already supplied counts; source/project-only choices, silence or a general destination confirmation do not. With a saved profile, show the actual source/project/Story type and every applicable remembered field with its saved value, using available business labels and values without extra discovery for display. Ask one concrete question: “These are your saved project fields: [actual field names and values]. Continue with them for this run, or change them?” Offer Continue with these fields / Change fields / Switch project, not a generic Use saved settings / Skip optional fields menu. Saved fields are the proposed working configuration, not a new optional-field questionnaire. If no additional field values are saved, say so explicitly; confirming that displayed configuration still counts as reused. That same confirmation resolves the decision without a second extra-fields question. Do not silently omit saved values; a changed value must be identified as this-run-only or a new future default, and an explicit removal must say whether it is for this run or future runs. A past run-only value is not a saved default, and this wording never changes metadata requiredness. Updates show the actual target/baseline and never apply create-only defaults. Distinguish remembered defaults from run-only values. Reuse one decision across an unchanged selected batch/resume; a project/type/settings switch needs its applicable decision.
5. While that decision is pending in a new preparation, keep one question in existing userRecovery and do not author, mark assembly verified or score. Its evidence stays in preparation.md; add no report/reviewer/check loop. Keep default jiraExportRequested=true unless the user explicitly requests no-Jira/stop, and resume automatically after answers without another continue/route question. Already-successful issue/profile-only recovery is different: save its verified configuration first, retaining unknown historical setup evidence; do not backtrack to this question, authoring, review or scoring. Any new preparation resolves its own decision.


Only honor preparation-only/no-Jira when the user explicitly requested it independently. Such a request still requires real destination/field data for a final scoreable .json4jira; incomplete drafts remain identified as drafts. The early settings decision is separate from final scored-content/upload confirmation, which remains required after scoring.

Read the actual user store on each new session; conversation files/history are not a substitute. An absent staffId never invalidates a profile or becomes an identity key. Keep legacy entries and use their facts only within established authenticated ownership, never by staffId alone; do not parse/store tokens. Existing baseline reads can supply project/type facts, and a missing update-capability entry never invalidates stable create facts.

Inspect actual Workspace operations, including supported native save/open/read actions, and use their lookup before reporting a limitation. Missing visible tool calls prove neither absence nor successful saving. Read-back is retrieving/opening the saved file, not a separate API; do not invent hidden APIs or native directives. A prior write proves write capability only. Report the concrete missing/failed operation, not a tool-name or absent-scope-label inference; do not fall back to conversation storage or overwrite an unreadable/uncertain user file. Confirmed not-found/empty means initialization, using actual folder creation or supported automatic parents when saving a populated profile. Retain the known Assembly facts for the exporter's success closeout; partial metadata can stay complete=false. The exporter's persistence reference owns save/merge/read-back, accessed through supported Skill resources, not assumed sibling paths.


Source is explicitly confirmed WPB/ALM/DATA/FCR/GO, not inferred from ticket prefix. Query calls use its lowercase almType. Follow the actual live schema: if a discovery tool exposes an identity input, use only its supported, genuinely platform-provided value; an unavailable query-only identity remains WAITING_TOOL, not a routine user question. Do not invent an identity argument, copy an old profile's staffId into a query or parse a JWT. No root staffId or staff-ID profile key is generated. Reporter is a separate Jira field: include `fields.reporter` only when the applicable operation requires a submitted value after valid update omission/baseline rules or the user explicitly requests it, and its actual supported value/encoding is resolved. First use a verified current value or trusted platform context. Only if a submitted Reporter value is required and still needs a staff ID, ask the user once for that value, then verify the accepted Reporter representation; never assume `reporter.name` or copy a query identity into the field. If the selected operation does not require/request Reporter, omit it; on update, omission does not clear the existing Reporter. Session IDs remain platform-owned and do not enter the file. Legacy jira-user-info.md supplies routing defaults, not field schema.

| Tool | Business inputs; actual parameter schema remains authoritative |
| --- | --- |
| java-base-mcp.queryJiraProjectsByName | almType, projectName |
| java-base-mcp.queryJiraIssueTypesByProject | almType, selected projectKey |
| java-base-mcp.queryJiraCreateMetaFields | almType, projectKey, and supported issueType or issueTypeId |

Reuse components independently:

| Component | Create/update reuse |
| --- | --- |
| Confirmed source/project, Story type name/ID, AC field ID, field identity/type and applicable option encodings | Reuse across modes for the same user/source/project/type. Combine profile facts with the actual baseline; no query merely because the mode changed. |
| Requiredness, writable operations, permissions and reusable defaults | Keep their evidenced operation scope. A create-only flag/default is not update permission or authorization to overwrite a baseline value. |
| Target Story content and attachments | Read the actual target baseline/inventory under the update procedure; profiles never replace these reads or select a target. |

When the profile plus existing verified evidence supplies the needed components, call none of the three discovery queries. For example, a saved create profile with the actual project/type/AC mapping can serve an update; absence of a separate update profile is not a reason to run discovery again. There is no TTL refresh. Query only a genuinely missing/inapplicable component, an explicit refresh or changed destination, or a precise actual schema error. Record which fact is missing and query only for it. One unambiguous project proceeds; multiple real choices need selection. Preserve actual distinct Story type IDs; no Story type blocks this route.

Do not rerun queryJiraProjectsByName/queryJiraIssueTypesByProject/queryJiraCreateMetaFields to manufacture an update capability record. queryJiraCreateMetaFields discovers create metadata; it cannot verify edit permission. Normal updates use the confirmed JSON update contract and actual target evidence, retaining operation-specific limits. Required getJiraInfos/readJiraAttachments baseline reads are separate from field discovery and still run when that target baseline has not been read.

Use only live exposed query arguments. Where metadata returns result.fields.values[], read those descriptors. Establish completeness from the contract or real closed pagination; do not invent paging controls. Retain all required descriptors, AC mapping and selected optional fields with actual IDs/name/schema/required/operations/default and used option ID/encoding. Do not infer requiredness from an omitted successful value. Create metadata is not independently verified edit permission.

## 2. Resolve values before JSON assembly

For an update the approved manifest first limits changes. Apply current explicit approved values, then actual baseline (omit unchanged fields), then applicable confirmed defaults/observed Jira defaults, then directly evidenced valid options. Ask only for unresolved required facts, using actual valid choices. Omit unknown optional fields; never invent IDs, business choices or placeholders. A profile/create default never authorizes overwriting existing relationships.

Resolve create Epic/no-Epic explicitly. A supplied Epic used only as the relationship target is not a requirements-source ticket. Follow [lightweight relationship validation](source-enrichment.md): verify a new, unverified key/source once with the supported getJiraInfos lookup and check actual type only when exposed. Business lookup success establishing that target accepts an empty/null/absent Description or AC; do not read its business content or attachments as a prerequisite for linking. Outer transport success with a business error is different; an ambiguous lookup is unverified, not an invalid link.

Reuse the same target/source and actual validation evidence across candidates and stages without another query. A changed target/source, explicit refresh or actual relationship error may require recovery; entering assembly/export, reusing a profile or seeing an empty Description does not. Preserve this evidence in existing context/assembly record, not an extra file. If the user also selects that Epic as a requirements source, read only the additional business evidence needed for that separate role; a content gap does not invalidate the confirmed relationship target.

Map Epic/Parent or other custom fields into **only** the property/ID/representation the active JSON/backend schema actually supports. Existence verification does not invent a writable field ID or relationship encoding. Do not invent wrapper fields from old direct tool arguments or let saved create defaults overwrite an existing target's relationships.

Complete the entry settings decision and its separate `optionalFieldsDecision` above with actual source/project/Story type, operation/update target, relationships and field values. An explicit unchanged current-run extra-field/default decision need not be asked again during assembly. A newly resolved or changed value that needs user choice returns to that decision. Final upload content is previewed and confirmed separately after scoring.

## 3. Write the complete canonical file

The confirmed contract uses the root AC field-ID string and distinct root `descPath`/`acPath` references to two Jira wiki files, with no customFields wrapper or root staffId. Use the [create template](../templates/story-json-template.json) or [update template](../templates/story-update-json-template.json); add `fields.reporter` only under the conditional Reporter rule above. Updates add root issueIdOrKey after issueType; creates omit it entirely. Encode the two rich-text files using [Jira text rules](jira-text-format.md) before scoring. This is a required input contract for correct field recognition, not an additional Q1–Q7 business criterion. The JSON is one object with a fields object, never a stringified Jira request.

| JSON location | Required value / relationship |
| --- | --- |
| jiraInstance | Selected supported lowercase Jira source; do not add almType/jiraType aliases. |
| projectKey and fields.project.key | The same actual confirmed project key. fields.project is an object. |
| issueType and fields.issuetype.id | Confirmed Story type name at the root, its actual queried ID string inside fields.issuetype. Preserve the exact lowercase issuetype key; never substitute its display name for the ID or hardcode the screenshot ID. |
| issueIdOrKey (updates only) | Exact nonempty existing ticket key confirmed by the user and actual baseline, placed after issueType. The I in Id is uppercase. It must match this candidate's confirmed source/target; never use an evidence-only ticket, cached target or another batch item. Creates omit this key, rather than send null/empty. |
| fields.summary | Supported reviewed title as a string. No root summary. |
| acceptanceCriteria | Root-level actual AC field ID string from applicable metadata/profile, not AC text, an array or a field descriptor object. Do not wrap it in customFields. |
| descPath | Workspace-relative path to the nonempty Description Jira wiki file under outputRoot, e.g. `<outputRoot>/<name>-description.jirawiki`. |
| acPath | Distinct Workspace-relative path to the nonempty AC Jira wiki file under outputRoot, e.g. `<outputRoot>/<name>-ac.jirawiki`; its content uses stable unique AC IDs and observable behavior. |
| fields.description and fields[acceptanceCriteria] | Omit both. The referenced files, not duplicate inline strings, supply those two bodies. |
| attachmentsJson | Root native JSON object for add only under [attachment operations](#4-confirmed-attachment-operations). |
| attachments | Empty array only for explicit no remote attachment change. Omit this property when using attachmentsJson.add. |

Resolve the AC field ID first, then store that exact ID as root acceptanceCriteria. For example, only when metadata really returns customfield_27708, acceptanceCriteria is that string, while the AC Jira wiki body is in the file at acPath. It is not a global default. Replace the <actual AC field ID> placeholder in the template with the complete observed ID; do not concatenate a guessed number. Missing mapping/file content or incompatible type blocks production precheck; never fall back to an old top-level AC array or put the ID into the business prose.

The root acceptanceCriteria maps only the AC field ID; it is not business text. Additional approved business values go in fields under their real metadata-confirmed IDs/types/options. Do not introduce a customFields wrapper, guess root aliases or duplicate values. Include only supported writable fields for this operation; Reporter follows its conditional required/requested rule. Preserve authorized optional fields/relationships in their confirmed schema locations. Updates preserve unchanged remote values through approved omission semantics rather than copying all baseline fields into the request.

Do not generate top-level staffId, summary, description, bddScenarios or customFields. The required root acceptanceCriteria is only the field-ID string, never the retired top-level AC text/array. Express supported BDD detail in the acPath file instead of maintaining a separate BDD object. Preserve all non-AC sections in the descPath file, including those originally following AC; AC has one authoritative wiki file. Complete rich-text encoding during assembly, before review/score; the SPEC uses a faithful Markdown view of the same content. There is no late Markdown-to-wiki conversion, stringified dynamicFieldsJson/attachmentsJson/issuesJson wrapper or regenerated payload at export. The root attachmentsJson object below is part of the saved JSON, never an additional score/export tool argument. Examples are not business facts or fixed environment IDs.

Save/read back <outputRoot>/story.json4jira and both distinct `.jirawiki` files referenced by its root paths. They must exist in the same session Workspace under outputRoot, contain the complete nonempty Jira wiki bodies, and match the paths recorded in state. The JSON is one real object, not a quoted JSON document or .md content. Remove every template placeholder. Record the actual paths in paths.storyJsonPath, paths.descWikiPath and paths.acWikiPath and reuse the unchanged JSON path across score/preview/export. Backend validation remains authoritative; use precise returned errors for bounded incremental correction.

## 4. Confirmed attachment operations

Save the approved upload plan in the canonical `story.json4jira` before review and scoring. Freeze it with that package through preview and export.

| Actual intent | File representation |
| --- | --- |
| Add reviewed SPECs for a create or update | Root `attachmentsJson` is a native object with only `add`, an array of objects containing actual `relativePath` and `fileName`. Both templates default to this operation. |
| Explicitly preserve remote attachments without uploading | Use `attachments=[]` and omit `attachmentsJson`. Score the current local SPEC through `specFilePath`. |

For add, omit the legacy `attachments` path array. Every `relativePath` is a readable Workspace-relative path to the reviewed SPEC and `fileName` matches its actual basename. Only upload the authorized current SPECs. Preserve all existing attachments. Older `replace` entries, `attachmentId` in an upload entry, or deletion instructions cannot be submitted. An unapplied plan using the old format must return to preparation for a current review, score and confirmation of the intended add or none plan. Preserve earlier evidence and reconcile unknown remote outcomes before considering another write.

## 5. Snapshot and update guard

Use the shared <historyRoot>/preparation.md as paths.planningPath and exportContext.assembly.recordPath for new candidates. Add a clearly labeled Assembly section for the actual storyJsonRevision with compact query/profile/schema facts, field meanings/option encoding, confirmed settings, relationship validation evidence and authorized attachment intent. Include the actual user-Workspace operation/destination binding and profile read outcome, selected profile identity/source/project/type key, settings confirmation, and the distinct optionalFieldsDecision status with its actual answer/approval evidence. For each supplied or reused extra field, retain the verified Jira field ID, business label, exact native value, any verified display value, operation scope and future-default versus this-run-only decision; record an explicit future change/removal. That compact snapshot, not a guess from the final JSON, feeds `confirmedDefaults` after issue success. Keep it populated even if the profile file was initially absent; the exporter must be able to save meaningful configuration after either create or update without repeating discovery. Reuse an unchanged verified section; do not create a new numbered assembly file on stage entry, candidate reuse or resume. Once a section has been used by review/score/export, retain it; a real mapping/settings/JSON change appends only the affected version-bound section under the workflow's preparation rules. Keep actual source/raw response pointers rather than duplicating full metadata or business bodies. Older internal numbered records remain valid through their actual state pointers. Before marking assembly verified, confirm its existing record stays under historyRoot and optionalFieldsDecision is provided/skipped/reused for these same settings; the exporter receives the exact record/profileKey and JSON revision.

An existing-ticket request never becomes a create. The user has confirmed root issueIdOrKey as the backend update selector: use that exact nonempty target key, verified against exportContext.target.ticketKey, baseline, confirmed source and project/type. Do not keep a general target-encoding WAITING_TOOL for this confirmed format. A missing/mismatched update key blocks the candidate; never remove it to retry as create. The same scored JSON path goes to the same score/export tools, without a separate issueIdOrKey tool argument or invented operation flag.

Preserve unchanged Summary/other baseline values and approved field omission semantics; the template's full business view does not authorize unrelated field changes. Do not treat create metadata as edit permission or omit a field required by the file contract. Apply [automatic Story/SPEC synchronization](existing-jira-update.md) and the [confirmed attachment operations](#4-confirmed-attachment-operations) before review/score. Bind the approved new SPEC paths and filenames to the confirmed source and ticket in the scored JSON and manifest. Material baseline content gaps and actual backend rejections remain precise pending work. None never disables local synchronization or primary specFilePath scoring. Never silently skip SPEC, invent controls, override explicit none or fall back to create. Ready unrelated candidates may continue preparation.

Persistent user-profile loading and missing-fact discovery belong here. After either issue create or update is actually successful, the exporter immediately attempts its profile read/merge/write/read-back procedure, independently of required attachment, linkage or queue failures/unknowns. Save only verified routing, operation-scoped reusable defaults and available metadata; incomplete metadata stays complete=false. Failed/unknown issue writes do not become successful profile evidence. Missing Assembly evidence alone does not make a successful write not_eligible: recover known source/project/type routing from the actual approved JSON and retained responses without inventing schema, permission or option descriptors. Preserve older confirmed facts and all other profile entries; report any remaining profile-persistence failure separately and recover only that save, never Jira/attachment/score calls.
