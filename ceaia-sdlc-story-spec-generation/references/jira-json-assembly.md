# Assemble final Jira JSON during Story generation

This step moves the former export-time project/type/field discovery, value resolution and payload assembly **before final scoring**. The exporter will only transmit the saved path. Use existing tools, no scripts, speculative fields or new query APIs.

## 1. Reuse profile components, then query only missing facts

### First entry and settings confirmation

Keep the default Jira-backed workflow. Do not offer a delivery-route choice between preparation-only and Jira-backed or recommend no-Jira because setup is missing. SDLC always prepares **Story**; an Epic/Bug profile never changes the issue type of this route. Use this short path before authoring a new candidate's canonical JSON:

1. Read the real persistent user-Workspace `ceaia-sdlc-jira/profiles.json`, trusted identity/context and already confirmed current-run settings first. Verify the returned user-level scope/destination, not just the basename. Select the matching authenticated user + Jira source + project + actual Story issue-type ID + operation capability. Profiles use canonical `issueType: {id, name}`; new Story entries also keep an identical `storyType` alias for older readers. Read a legacy `storyType` as Story only; conflicting aliases are a precise data gap, never a guessed match. Preserve the profiles array: several projects/sources/types may coexist; neither the last saved entry nor a single global default selects this run. Multiple applicable destinations need an actual project/settings selection. A profile for another issue type may share only applicable stable project facts, never its type-specific schema/defaults. A create/update capability scopes permissions/defaults, not the identity of stable project/type/mapping facts; one operation never silently changes the other operation's defaults.
2. With no applicable settings, guide the user through **source → project → optional extra fields**. Ask only unresolved business inputs: Jira source (WPB/ALM/DATA/FCR/GO), then project name or already known key. Never ask for staffId or add it to setup; authentication comes from trusted platform context. Already supplied facts skip their questions. A project name is sufficient; do not ask users for technical schema, issue-type IDs or AC field IDs.
3. Use the existing discovery tools only for missing project/Story-type/field facts below. A confirmed project key can feed supported type/metadata queries directly; do not invent a project-key argument for the project-name query. Once the applicable fields are known, offer the optional third question, for example: “这个项目还有想预设的字段吗？例如 Epic Link、Story Type（仅该项目支持的字段）；可以填写，也可以选择‘暂不设置’。” Show only real supported fields/choices, using their user-facing labels. `Story Type` here is a metadata-confirmed custom/subtype field, never a switch from Story to Epic/Bug. Preserve any requested unsupported field as a precise gap; do not invent its ID/encoding. Skipping leaves unknown optional fields absent and does not block generation; separately resolve required facts. If no Epic was otherwise selected for a create, “暂不设置” also confirms no Epic for this run, satisfying the later Epic/no-Epic decision without another question; do not erase an explicit current relationship choice. Record whether supplied values are reusable defaults or explicitly for this run only.
4. With existing applicable settings, show the selected source/project, fixed Story type and saved reusable field values **before creating canonical business files**, and ask: “本次是否沿用这些字段？可以直接沿用、修改字段，或切换项目；也可以指定仅本次使用。” A saved profile is a proposal, not current-run confirmation. One explicit current-run approval of this displayed unchanged configuration covers its selected batch; resume and each candidate do not repeat it. Current explicit user choices may satisfy the same decision when they already unambiguously cover those values. A pending decision remains WAITING_USER; do not treat silence as approval or overwrite other profiles when switching. Updates also require this settings decision when only a create-capability profile exists: show its reusable destination/type/mapping facts plus the real target/baseline, label create-only defaults as inapplicable, and apply only the approved delta. An “沿用” response never turns create defaults into update values or authorizes overwriting existing fields.
5. Preserve Jira intent and pending questions: jiraExportRequested defaults to true, while an explicit user no-export request stays false. Once the requested settings decision and missing facts arrive, resume assembly automatically; no extra continue or route confirmation. Missing setup is not a completed final JSON or score. A missing technical mapping/service capability is WAITING_TOOL, not a reason to switch routes or have the user invent IDs.

Only honor preparation-only/no-Jira when the user explicitly requested it independently. Such a request still requires real destination/field data for a final scoreable .json4jira; incomplete drafts remain identified as drafts. The early settings decision is separate from final scored-content/upload confirmation, which remains required after scoring.

For create and update, read the same real user-level profile store even in a new session; chat history, an in-memory copy or a conversation file cannot substitute for this cross-session read. Match the actual authenticated user/source/project/Story type, then reuse applicable components; a create capability does not invalidate stable facts during update. Existing-target reads can supply actual project/type facts. Use the platform's trusted opaque subject or genuinely user-isolated namespace without parsing/storing tokens. staffId is neither a required profile field nor a fallback profile key in SDLC. Preserve legacy fields/entries without making them setup prerequisites; reuse their facts only when current authenticated scope establishes ownership, never by staffId alone. Missing staffId does not invalidate a new or legacy profile. If authenticated scope cannot be established, report that technical gap instead of asking users for identity. Without a supported user-level persistence tool, use supported current evidence for this run and report the exact persistence limitation; never claim durable storage or silently replace it with conversation storage.

A confirmed not-found file/parent or empty profiles array means no saved configuration yet, not unavailable persistence. Keep verified current identity/settings and available metadata; ask/query only the remaining gaps. Retain the populated Assembly snapshot for the exporter's create-or-update save immediately after an actually confirmed issue write, including partial attachment/linkage/queue outcomes. Incomplete metadata does not prevent saving known routing and confirmed reusable defaults with metadata.complete=false; an empty template is not a meaningful saved profile. A denied read, service failure or malformed existing JSON is different: preserve that error and existing data; never overwrite uncertain/corrupt storage with an empty template. The exporter owns its `references/workspace-profile.md` read/merge/write/read-back procedure. Independently packaged Skills use the supported cross-Skill access in workflow-contract, not assumed sibling access.

Source is explicitly confirmed WPB/ALM/DATA/FCR/GO, not inferred from ticket prefix. Query calls use its lowercase almType. Follow the actual live schema: if a tool exposes an identity input, only its supported, genuinely platform-provided value may be used. Do not invent an identity argument, copy an old profile's staffId into a query, collect it from the user, or parse a JWT to obtain it. If an actually required identity is unavailable from trusted platform context, record WAITING_TOOL with the exact injection/schema gap; do not run extra project/type/metadata queries to obtain identity. This does not claim the server's schema has removed every identity parameter. Query/profile identity is not a Story field: omit root staffId and fields.reporter for both create and update. Do not recover reporter from old templates, profiles or baseline copies. Session IDs remain platform-owned and do not enter the file. Legacy jira-user-info.md supplies routing defaults, not field schema.

| java-base-mcp.queryJiraIssueTypesByProject | almType, selected projectKey |

Reuse components independently:

| Component | Create/update reuse |
| --- | --- |
| Confirmed source/project, Story type name/ID, AC field ID, field identity/type and applicable option encodings | Reuse across modes for the same user/source/project/type. Combine profile facts with the actual baseline; no query merely because the mode changed. |
| Requiredness, writable operations, permissions and reusable defaults | Keep their evidenced operation scope. A create-only flag/default is not update permission or authorization to overwrite a baseline value. |
| Target Story content and attachments | Read the actual target baseline/inventory under the update procedure; profiles never replace these reads or select a target. |

When the profile plus existing verified evidence supplies the needed components, call none of the three discovery queries. For example, a saved create profile with the actual project/type/AC mapping can serve an update; absence of a separate update profile is not a reason to run discovery again. There is no TTL refresh. Query only a genuinely missing/inapplicable component, an explicit refresh or changed destination, or a precise actual schema error. Record which fact is missing and query only for it. One unambiguous project proceeds; multiple real choices need selection. Preserve actual distinct Story type IDs; no Story type blocks this route.

Do not rerun queryJiraProjectsByName/queryJiraIssueTypesByProject/queryJiraCreateMetaFields to manufacture an update capability record. queryJiraCreateMetaFields discovers create metadata; it cannot verify edit permission. Normal updates use the confirmed JSON update contract and actual target evidence, retaining operation-specific limits. Required getJiraInfos/readJiraAttachments baseline reads are separate from field discovery and still run when that target baseline has not been read.

Use only live exposed query arguments. Where metadata returns result.fields.values[], read those descriptors. Establish completeness from the contract or real closed pagination; do not invent paging controls. Retain all required descriptors, AC mapping and selected optional fields with actual IDs/name/schema/required/operations/default and used option ID/encoding. Do not infer requiredness from an omitted successful value. Create metadata is not independently verified edit permission.

## 2. Resolve values before JSON assembly

For an update the approved manifest first limits changes. Apply current explicit approved values, then actual baseline (omit unchanged fields), then applicable confirmed defaults/observed Jira defaults, then directly evidenced valid options. Ask only for unresolved required facts, using actual valid choices. Omit unknown optional fields; never invent IDs, business choices or placeholders. A profile/create default never authorizes overwriting existing relationships.

Resolve create Epic/no-Epic explicitly. A supplied Epic used only as the relationship target is not a requirements-source ticket. Follow [lightweight relationship validation](source-enrichment.md): verify a new, unverified key/source once with the supported getJiraInfos lookup and check actual type only when exposed. Business lookup success establishing that target accepts an empty/null/absent Description or AC; do not read its business content or attachments as a prerequisite for linking. Outer transport success with a business error is different; an ambiguous lookup is unverified, not an invalid link.

Reuse the same target/source and actual validation evidence across candidates and stages without another query. A changed target/source, explicit refresh or actual relationship error may require recovery; entering assembly/export, reusing a profile or seeing an empty Description does not. Preserve this evidence in existing context/assembly record, not an extra file. If the user also selects that Epic as a requirements source, read only the additional business evidence needed for that separate role; a content gap does not invalidate the confirmed relationship target.

Map Epic/Parent or other custom fields into **only** the property/ID/representation the active JSON/backend schema actually supports. Existence verification does not invent a writable field ID or relationship encoding. Do not invent wrapper fields from old direct tool arguments or let saved create defaults overwrite an existing target's relationships.

Complete the entry settings decision above with actual source/project/Story type, operation/update target, relationships and field values. An explicit unchanged current-run choice need not be asked again during assembly. A newly resolved or changed value that needs user choice returns to that decision. Final upload content is previewed and confirmed separately after scoring.

## 3. Write the complete canonical file

The developer's latest user-confirmed contract supersedes the earlier nested-map/Markdown samples: acceptanceCriteria is the root AC field-ID string, with no customFields wrapper; omit root staffId and fields.reporter. Use the [create template](../templates/story-json-template.json) or [update template](../templates/story-update-json-template.json). Updates add root issueIdOrKey after issueType; creates omit it entirely. Encode rich text using [Jira text rules](jira-text-format.md) before scoring. This is a required input contract for correct field recognition, not an additional Q1–Q7 business criterion. It is one JSON object with a fields object, never a stringified Jira request.

| JSON location | Required value / relationship |
| --- | --- |
| jiraInstance | Selected supported lowercase Jira source; do not add almType/jiraType aliases. |
| projectKey and fields.project.key | The same actual confirmed project key. fields.project is an object. |
| issueType and fields.issuetype.id | Confirmed Story type name at the root, its actual queried ID string inside fields.issuetype. Preserve the exact lowercase issuetype key; never substitute its display name for the ID or hardcode the screenshot ID. |
| issueIdOrKey (updates only) | Exact nonempty existing ticket key confirmed by the user and actual baseline, placed after issueType. The I in Id is uppercase. It must match this candidate's confirmed source/target; never use an evidence-only ticket, cached target or another batch item. Creates omit this key, rather than send null/empty. |
| fields.summary | Supported reviewed title as a string. No root summary. |
| fields.description | Supported non-AC business content as one Jira wiki string, e.g. h2. User Story, with real line breaks represented by JSON escaping. No unintended Markdown headings outside code/literal examples, array or JSON-encoded inner document. |
| acceptanceCriteria | Root-level actual AC field ID string from applicable metadata/profile, not AC text, an array or a field descriptor object. Do not wrap it in customFields. |
| fields[acceptanceCriteria] | The actual AC Jira wiki string, e.g. * *AC-001*: Given … When … Then …, with stable unique IDs and observable behavior. The mapped property must exist and be nonempty. |
| attachmentsJson | Root JSON object for confirmed add/replace operations under [attachment operations](#4-confirmed-attachment-operations). Do not stringify it. |
| attachments | Only the confirmed explicit-none form []; omit attachmentsJson. Active add/replace omits this legacy path array. |

Resolve the AC field ID first, then use that exact string as the key in fields and store AC content there. For example, only when metadata really returns customfield_27708, acceptanceCriteria is that string and fields.customfield_27708 contains the AC Jira wiki. It is not a global default. Replace both identical <actual AC field ID> placeholders in the template with the complete observed ID; do not concatenate a guessed number. Missing mapping/value or incompatible type blocks production precheck; never fall back to an old top-level AC array or put the ID into the business prose.

The root acceptanceCriteria maps only the AC field ID; it is not business text. Additional approved business values go in fields under their real metadata-confirmed IDs/types/options. Do not introduce a customFields wrapper, guess root aliases or duplicate values. Include only supported writable fields for this operation; reporter is excluded from both modes. Preserve authorized optional fields/relationships in their confirmed schema locations. Updates preserve unchanged remote values through approved omission semantics rather than copying all baseline fields into the request.

Do not generate top-level staffId, summary, description, bddScenarios or customFields. The required root acceptanceCriteria is only the field-ID string, never the retired top-level AC text/array. Express supported BDD detail in the mapped AC Jira wiki instead of maintaining a separate BDD object. Preserve all non-AC sections in fields.description, including those originally following AC; AC has one authoritative mapped field. Complete rich-text encoding during assembly, before review/score; the SPEC uses a faithful Markdown view of the same content. There is no late Markdown-to-wiki conversion, field partition, stringified dynamicFieldsJson/attachmentsJson/issuesJson wrapper or regenerated payload at export. The root attachmentsJson object below is part of the saved JSON, never an additional score/export tool argument. Examples are not business facts or fixed environment IDs.

Save/read back <outputRoot>/story.json4jira. It is one real JSON object, not a quoted JSON document and not a file with .md content. Remove every template placeholder. Record the actual immutable path in paths.storyJsonPath and reuse it exactly across score/preview/export. Backend validation remains authoritative; use precise returned errors for bounded incremental correction.

## 4. Confirmed attachment operations

The user has tested the JSON route's root attachmentsJson object and confirmed that readJiraAttachments returns the original attachment IDs. Use this confirmed contract directly; routine add/replace does not wait for another schema or capability proof. Keep the operation inside the canonical story.json4jira before review/scoring, and freeze it with that package through preview/export.

| Intended action | Exact file representation |
| --- | --- |
| Create or a proven first SPEC on an existing ticket | attachmentsJson.add is an array of objects with relativePath and fileName. |
| Replace an affected existing SPEC | attachmentsJson.replace is an array of objects with attachmentId, relativePath and fileName. |
| Explicit preservation of remote attachments | attachments=[]; omit attachmentsJson entirely. Do not invent an empty-object sentinel. |

attachmentsJson is an object, not a JSON-encoded string or a tool argument. For add/replace omit the legacy attachments path array so the same file is not submitted through two upload controls. Include only the authorized operation entries, not invented delete properties or an empty counterpart array. Every relativePath is the actual reviewed Workspace-relative SPEC path; fileName equals its basename. The create template defaults to add; the update template defaults to replace. If a complete inventory establishes no related SPEC and no unresolved possible SPEC, change that update to add and omit attachmentId.

Each replace entry's attachmentId comes from readJiraAttachments for this exact confirmed source+ticket and is bound to the read original content classified as an affected related SPEC under [existing-update rules](existing-jira-update.md#identify-spec-originals-before-selecting-replacements). Keep actual ID → output mappings in the manifest; never use a cached ID from another ticket, filename/MIME/spec-substring matching or an invented ID. Preserve every non-SPEC and unselected original. Unreadable/ambiguous originals or an incomplete inventory still require precise evidence/selection recovery; do not treat them as no SPEC and fall through to add. Distinct originals with different obligations retain distinct outputs unless reviewed many-to-one preservation is explicitly authorized.

Replacement retains the upload-before-delete requirement: the backend operation must upload the new file successfully before deleting only its mapped old ID. The user's tested input format does not itself prove atomicity or a completed operation, and routine replace needs no additional capability proof. Submit the unchanged scored JSON path and inspect actual results; never call a separate delete/legacy API. An upload failure/unknown result preserves the old original. Upload success with old removal failed/unknown is partial, not full replacement; preserve results and recover only the pending effect without replaying a successful Story write or upload. An actual backend rejection is the precise supported-contract error to resolve, not permission to omit replacement, override none or fall back to create. A local score-only SPEC uses specFilePath and is not added to uploads solely for scoring.
